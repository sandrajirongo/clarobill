# Email Architecture

ClaroBill uses two email providers with non-overlapping roles:

| Provider | Role | Where |
|---|---|---|
| **Loops** | Marketing emails + transactional product emails | `apps/web/src/lib/loops.ts` |
| **SendGrid** | Referral credit notifications (plain HTML, no template) | `apps/web/src/app/api/stripe/webhook/route.ts` |
| **Engine (SendGrid)** | PDF report delivery | `apps/engine/app/services/report_generator.py` |

---

## Loops

Loops handles all lifecycle emails: onboarding, payment receipts, follow-up sequences, and marketing.

### Contact management

Supabase has a native Loops integration configured in the dashboard. It automatically syncs new `auth.users` rows to Loops contacts on sign-up — `createLoopsContact()` is only called from the web app when additional properties need to be set alongside creation (e.g. marketing opt-in from the lead magnet form).

| Function | When called |
|---|---|
| `createLoopsContact(email, properties)` | Lead magnet form submission (`/api/lead-magnet`) |
| `updateLoopsContact(email, properties)` | Profile update, plan type change |
| `sendLoopsTransactional(id, email, vars)` | Payment receipt immediately after `checkout.session.completed` |
| `sendLoopsEvent(email, eventName, props)` | Behavior triggers — fires journey-based workflows |

All helpers are no-ops when `LOOPS_API_KEY` is unset. `sendLoopsTransactional` is also a no-op when `transactionalId` is empty (guarding against unconfigured `LOOPS_PAYMENT_EMAIL_ID`).

### Events fired

| Event name | Fired from | Triggers |
|---|---|---|
| `payment_completed` | Stripe webhook | 1-day "check your report" + 30-day "share with a friend" workflows |

Additional events (sign-up, bill_uploaded, etc.) are fired via the Supabase Loops integration, not the `sendLoopsEvent()` helper.

### Transactional email IDs

| Env var | Purpose |
|---|---|
| `LOOPS_PAYMENT_EMAIL_ID` | Payment receipt — sent immediately on `checkout.session.completed` |
| `LOOPS_BILLING_TRAPS_EMAIL_ID` | (Reserved) educational follow-up email about common billing traps |

These IDs are the Loops dashboard template identifiers. Create the templates in Loops, copy the ID, and set the env var. The emails are never committed to the repo — see the `feedback_email_files_not_committed` memory.

## SendGrid (referral credit notification)

The referral credit email is sent directly from the Stripe webhook handler via SendGrid's `/v3/mail/send` endpoint — no template, just inline HTML generated by `referralCreditEmailHtml()`.

**Why SendGrid here and not Loops?**  
The referral credit email contains a dynamic dollar amount and cumulative earnings that vary per user. At the time this was built, the Loops transactional template system was already used for the payment receipt. A second template for referrals would have required a Loops template with the same variables — SendGrid was already configured for report delivery so reusing it avoided adding another template.

**No-op behavior:** If `SENDGRID_API_KEY` is unset, a warning is logged and the email is skipped. The referral credit is still applied to the account.

## Engine: PDF report delivery

The engine sends the PDF report as an email attachment via SendGrid after generation. This flow is triggered by the Stripe webhook calling `POST /api/v1/bills/{billId}/report` on the engine.

Configuration:
- `SENDGRID_API_KEY` — SendGrid API key (same key as the web app's)
- `SENDGRID_FROM_EMAIL` — From address (defaults to `noreply@clarobill.com`)

---

## Email file policy

Email templates, MJML source files, and Loops campaign copy are **never committed to the repository**. Output them in chat or save to Desktop only. See the `feedback_email_files_not_committed` memory.

---

## Local development

All email sends are silent no-ops when the relevant env var is not set:
- Loops: `LOOPS_API_KEY` must be set to send
- SendGrid: `SENDGRID_API_KEY` must be set to send

For local testing, set `LOOPS_API_KEY` to a test key or use the Loops sandbox. SendGrid has no sandbox mode — use a real address or omit the key.
